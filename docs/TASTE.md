# Design & Code Taste — Anvil Starter Kit

> This document defines the aesthetic and code conventions that make Anvil feel like it was written by one person, not generated by a hundred different AI prompts. It is read by AI agents (via `.ai/guidelines/`) and by humans as onboarding.

---

## Code Taste

### Explicit over clever
- No unnecessary abstraction layers. If the code is simple, leave it simple.
- A method that needs a comment to explain *what* it does should be renamed, not commented.
- Comments explain *why*, not *what*.

### Actions over services
- One invokable class per business operation: `App\Actions\CreateUser`, `App\Actions\SendInvitation`.
- No `UserService` with 15 methods. If you have 15 operations, you have 15 Action classes.

### Immutable by default
- `readonly` properties everywhere they make sense.
- `CarbonImmutable` is the default date class (via `nunomaduro/essentials`).
- Avoid mutating input arrays — return new values instead.

### Strict types everywhere
- `declare(strict_types=1)` at the top of every PHP file, no exceptions.
- Full type hints on all parameters, return types, and properties.
- Use PHP 8.3+ enums for any column or value with a fixed set of options.

### Naming
- Classes: `PascalCase`, descriptive nouns — `CreateUser`, `Role`, `UserResource`
- Methods: `camelCase`, verb-first — `updateProfile()`, `sendVerification()`
- Database columns: `snake_case` — `email_verified_at`, `app_authentication_secret`
- No abbreviations — `$user` not `$u`, `$authentication` not `$auth` (except the `Auth` facade)

## UI/UX Taste

### Design tokens, not magic numbers
- Spacing, type scale, and colors are defined once in Tailwind config.
- Reference tokens everywhere: `px-4`, `text-sm`, `text-primary-600`.
- **Never** use arbitrary values like `px-[13px]` or `text-[#3b82f6]`.

### Empty states and loading states are not optional
- Every list view must define what it looks like with zero items.
- Every async operation must show a loading indicator.
- These are part of the definition of done for any list/table/grid component.

### Destructive actions require confirmation
- Delete, revoke, disable, ban — any action that cannot be easily undone gets a confirmation modal.
- Confirmation style must be consistent between the Livewire app and the Filament panel.
- Use red/danger color for destructive action buttons.

### Flux first
- `livewire/flux` components are the default UI kit for the customer-facing app.
- A custom component is justified only when Flux genuinely cannot handle the use case.
- When creating a custom component, document the justification.

### Consistent layouts
- **Guest layout**: Used for auth pages (login, register, forgot password). Centered card, minimal chrome.
- **App layout**: Used for authenticated pages. Sidebar or top nav, user menu, dark mode toggle.
- Both layouts share the same design tokens and component library.

### Dark mode
- Supported via a cookie-persisted toggle.
- Every component must look correct in both light and dark mode.
- Test both modes when adding or modifying UI.

## Decision Records

When you deviate from these conventions, document the reason in the PR description or in a comment. Undocumented deviations will be questioned in review.
